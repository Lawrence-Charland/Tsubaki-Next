# Tsubaki-Next

[English](README.md)

Tsubaki 校验和工具的重写版，核心是校验和计算本身：覆盖大部分普通摘要与密钥哈希，
可以计算单个文件、递归整棵目录树，也可以读取列表文件里的路径；这些输入源能在一次
运行中自由组合、并行计算，目录扫描还支持排除项。

结果是一份*清单*（manifest，也就是 `sum` 写出的校验和文件）：`<校验和> <路径>`
行，加上一块 `#` 报告。因为清单只是一个普通文件，同一套工具还能对它做两件事：

- `verify` 按清单里的路径重新计算，报出 `changed` 和 `unsure`。它方便，直接回答
  “有没有变化”；产出又是一份刷新后的清单，可以归档，也可以再次校验。它的粒度较粗：
  每个路径只给一个结论，而 `unsure` 同时涵盖“清单本来就没有校验和”和“这次
  算不出来”。
- `cmp` 完全不碰文件，只比较两份清单。它详细，回答的是“具体变了什么”：`[!]`
  修改、`[D]` 移动/复制/合并/改名（按校验和分组）、`[U]` 删除或新增、`[=]` 相同。
  详细的代价是不方便——你得先有两份清单，而且它无法判断当前文件与其中任何一份的
  差异。

两者可以衔接：`verify` 产出最新的清单，`cmp` 再把它和旧清单做细粒度比较。

## 构建

需要 CMake 3.28+（这是 `CMakePresets.json` 的要求；`CMakeLists.txt` 本身只要求
3.10）、支持 C++23 的编译器、OpenSSL（只链接 `libcrypto`；密钥哈希需要 3.0 起的
`EVP_MAC`），预设里用的是 Ninja。

```sh
cmake --preset linux-gcc-release
cmake --build --preset linux-gcc-release
```

第一次配置会从 GitHub 拉取
[LC-ArgParser](https://github.com/Lawrence-Charland/LC-ArgParser)，所以需要联网
一次；拉下来的副本放在 `build/<预设名>/_deps`，之后复用。没有网络时，把 CMake
指向本地检出即可：

```sh
cmake --preset linux-gcc-release \
      -DFETCHCONTENT_SOURCE_DIR_LC-ARGPARSER=/path/to/LC-ArgParser
```

可执行文件在 `build/linux-gcc-release/tsubaki`。另有布局相同的
`linux-gcc-debug` 预设。

## 用法

```
tsubaki sum [选项] <算法> <文件|目录>...
tsubaki verify [选项] <校验和文件|->   （`-` 表示 stdin，需要 -u）
tsubaki cmp [选项] <左清单> <右清单>
tsubaki --help
tsubaki --version
tsubaki --algorithm
```

子命令是必需的：`sum` 计算校验和，`verify` 复核 `sum` 写出的结果文件，`cmp` 比较
两份这样的结果文件。只有 `--help`、`--version` 和 `--algorithm`（`-a`）不需要子命令；
子命令位置上换成别的词会按未知子命令报错。这三个都在校验之前检查，所以也优先于其它
参数错误：`tsubaki -a junk` 照样打印算法表并退出 0。同时给出多个时，`--help` 优先于
`--version`，两者又都优先于 `--algorithm`。

下文直到 [校验](#校验) 都在讲 `sum`；`verify` 复用同一份校验和文件格式以及
`-v`、`-t`、`-k`、`-K`、`-o`、`-u` 这几个选项。`cmp` 复用同一份格式，但它要两份文件，
而且只接受 `-o` 和 `-c`。

`算法` 是位置参数，它后面的输入也是。输入可以是目录、文件，或者 `-`（标准输入），
可以混着写。

建议的写法是：算法放最前，然后一口气写完全部输入源，最后再写选项。

```sh
tsubaki sum sha256 目录1 文件2 - -e build -l old.txt
```

输入一个都不给也行：`tsubaki sum sha256` 会以一条空流跑完，只打印报告块，各计数
全为 0。

### 算法

`none` 只列文件不计算，所有文件都计入 `Not hashed`。其余名字要么是普通摘要，要么
是密钥哈希。

普通摘要：

```
md5  sha1  sha224  sha256  sha384  sha512  sha3_256  sha3_512
blake2b512  blake2s256
```

密钥哈希：

```
hmac_md5  hmac_sha1  hmac_sha224  hmac_sha256  hmac_sha384  hmac_sha512
hmac_sha3_256  hmac_sha3_512  blake2b512_mac  blake2s256_mac
```

`hmac_*` 是"前缀后面那个摘要的 HMAC"，所以 `hmac_sha3_512` 就是 HMAC-SHA3-512。
`blake2b512_mac` 和 `blake2s256_mac` 是带密钥的 BLAKE2b-512 与 BLAKE2s-256；带密钥
的 BLAKE2 与不带密钥的 `blake2b512`/`blake2s256` 结果不同，因为密钥参与了压缩函数。

密钥算法不给密钥会按命令行错误处理：退出码 64，并提示 `needs a key`。给普通摘要
配密钥则只是警告，密钥被忽略。

摘要与 `openssl dgst -<名字>` 一致，HMAC 与 `openssl dgst -<摘要> -hmac <密钥>`
一致，BLAKE2 MAC 与 `openssl mac -macopt key:<密钥> BLAKE2BMAC`（或 `BLAKE2SMAC`）
一致。输出是小写十六进制，长度由算法决定。

`tsubaki -a`（`--algorithm`）把同一批名字打成两列表格（`ALGORITHM`、`KEYED`），内容
直接从定义算法的那个宏生成，所以跟着实现走，而不是把上面的列表再抄一遍。

### 选项

| 选项                            | 含义                                                               |
| ------------------------------- | ------------------------------------------------------------------ |
| `-h`, `--help`                  | 打印帮助后退出                                                     |
| `-V`, `--version`               | 打印版本后退出                                                     |
| `-a`, `--algorithm`             | 打印算法列表及每个是否带密钥，然后退出                             |
| `-v`, `--verbose`               | 在 stderr 上显示实时进度（`none` 时不显示）                        |
| `-t<n>`, `--thread=<n>`         | 工作线程数，正整数，默认为硬件并发数（取不到时用 1）               |
| `-k<key>`, `--key=<key>`        | 密钥算法的密钥；普通算法会警告并忽略                               |
| `-K<file>`, `--key-file=<file>` | 从 `<file>` 读密钥（`-` 表示 stdin），去掉尾部 CR/LF；普通算法忽略 |
| `-o<file>`, `--output=<file>`   | 结果写入 `<file>`（新建或截断），而不是 stdout（`sum`）、`<校验和文件>.verify`（`verify`）或 `<左>_to_<右>.cmp`（`cmp`）；`-` 表示 stdout |
| `-u<algo>`, `--use-algo=<algo>` | 用 `<algo>` 校验，而不是清单里的 `Algorithm:` 头（仅 `verify`）    |
| `-c`, `--canonical`             | 比较前把两边路径变成绝对路径、解析软链接并规整分隔符，仅 `cmp` 使用       |
| `-e<path>`, `--exclude=<path>`  | 遍历目录时跳过 `<path>` 及其下所有内容，可重复。                   |
| `-l<file>`, `--list=<file>`     | 从 `<file>` 读取路径列表，可重复                                   |
| `-s`, `--follow-symlinks`       | 跟随指向目录的符号链接                                             |
| `-f`, `--force-rescan`          | 重算输入列表中已有的校验和                                         |

别名：`--threads`、`--excludes`、`--lists`。

`verify` 接受 `-v`、`-t`、`-k`、`-K` 和 `-o`，含义与 `sum` 相同，另外用 `-u` 指定
算法。它没有算法和文件位置参数，也不接受 `-e`、`-l`、`-s`、`-f`：路径、不给 `-u`
时的算法以及无条件重算都来自校验和文件。这份清单也可以写成 `-`，从 stdin 读；但那样
就没法先读出 `Algorithm:` 头，所以 `-` 输入必须配 `-u`。

`cmp` 只接受 `-o` 和 `-c`。它完全不计算哈希，所以没有算法、密钥、线程或扫描类
选项；`-v`、`-t`、`-k`、`-K`、`-e`、`-l`、`-s`、`-f` 都会按命令行错误拒绝，退出码
64。它的两个位置参数是要比较的结果文件，不是待计算的路径。

解析本身由独立的小库
[LC-ArgParser](https://github.com/Lawrence-Charland/LC-ArgParser) 完成；
`include/cmdline.hpp` 里只负责描述本程序的命令行。

### 选项的取值

长选项用 `=` 赋值，短选项用粘滞写法：

```sh
tsubaki sum sha256 . --exclude=build --list=old.txt
tsubaki sum sha256 . -ebuild -lold.txt
tsubaki sum hmac_sha256 . --key=secret
```

分离式写法取的是开关后面紧跟的那一串普通参数，取几个由选项决定：`-t`、`-k`、
`-K`、`-o` 和 `-u` 只取一个，`-e` 和 `-l` 你给几个取几个，直到碰到下一个还在队列里的
开关。

```sh
tsubaki sum sha256 . -e a b c -l list1 list2   # 三个排除项、两个列表
tsubaki sum hmac_sha256 -k secret .            # 一个密钥，不再往后取
```

这里 `-e` 会在 `-l` 前停住，因为 `lists` 排在 `excludes` 之后评估；每个条目各取
自己那一串值。

匹配不到任何条目的开关不会被当成选项错误：它仍然是一个普通参数，会被位置参数收
进去，然后按“文件不存在”报错。所以把 `--exclude` 敲成 `--exlude=build` 时，错误
出现在报告的错误块里，而不是一句选项错误。

### 密钥哈希

密钥从下面两处之一取得，不能同时给：

- `--key` 接受字面字符串：参数里的字节原样当密钥，不做十六进制或转义解码，
  所以 `-k 00ff` 得到的是四字节密钥 `0`、`0`、`f`、`f`。不建议这样做（至少本人不喜欢），
  因为这可能使密钥泄漏在 shell 历史记录或 `/proc` 下。
- `--key-file` 从文件读，路径写 `-` 时从 stdin 读。整个流都会读完，尾部连续的
  CR/LF 会被去掉，所以 `echo secret > key` 得到的是 `secret`；中间换行、NUL 字节
  和尾随空格都仍然属于密钥。文件不存在、读不了或是空文件，退出码 66。

`-k` 和 `-K` 同时给会按命令行错误拒绝，退出码 64；`-K -` 与 `-` 输入同时出现也
一样，同一条 stdin 只能指定一次。配普通摘要时两种写法都只警告并忽略，`-K` 指定的
文件根本不会被打开。

一次运行所有文件共用一个密钥；想用两个密钥校验同一棵树，就分别跑两次。

带密钥的 BLAKE2 对密钥长度有上限：`blake2b512_mac` 最多 64 字节，
`blake2s256_mac` 最多 32 字节。超了会在打开任何文件之前按命令行错误拒绝，退出码 64；
HMAC 不限制长度。

`--key` 把密钥放在命令行上：进程运行期间，机器上的任何用户都能从 `ps` 或
`/proc/<pid>/cmdline` 读到它，shell 还会在历史文件里留一份。`--key-file` 能避开
这两处，但文件本身只和它的权限一样私密（建议 `chmod 600`）。无论哪种写法，运行
期间密钥都待在进程内存里，绝对不会留在输出结果的任何地方。不要在多用户主机上使用真正的密钥。

密钥哈希的输出与普通摘要完全一样：`<校验和> <路径>`，报告块里写的是所选算法。
没有任何字段标记某一行是密钥哈希，只有随行的那份报告块里的算法名能区分。

### 校验

`verify` 重新读取 `sum` 写出的校验和文件，并重算其中列出的每一条路径：

```sh
tsubaki verify sums.txt                 # 写出 sums.txt.verify
tsubaki verify sums.txt -o -            # 把刷新后的校验和打到 stdout
tsubaki verify sums.txt -o new.txt      # 写到 new.txt
tsubaki verify sums.txt -u sha256       # 不用文件头，改用 sha256
cat sums.txt | tsubaki verify - -u sha256   # 从 stdin 读清单
```

清单可以写成 `-`，表示从 stdin 读。`Algorithm:` 头没法在不消耗后续路径数据的前提下先
读出来，所以 `-` 清单必须配 `-u`，否则退出 64；同一条 stdin 也只能指定一次，`-` 清单
再配 `-K -` 会被拒绝。不给 `-o` 时输出按输入命名，输入是 stdin 时就是 `stdin.verify`。

算法取自文件里的 `# Algorithm:` 头，除非用 `-u`（`--use-algo`）指定。强制指定的
算法会在 stderr 上说明，并完全取代文件头，所以 `-u` 也能校验完全没有头的清单，或者
头已经过时的清单；名字不认识则退出 64。也允许指定 `none`，但那样不会计算任何哈希：
每条路径都算作 `Not hashed`，并且全部记入 unsure。路径、`<NONE>` 标记和注释行的读法
与 `-l` 完全一致，区别在于每一条校验和都会重算：`verify` 隐含 `--force-rescan`。

输出形状与 `sum` 相同：每个处理过的文件一行 `<校验和> <路径>`，随后是报告块。
报告里多出两个字段：

```
# Changed:           1
# Unsure:            0
```

*changed* 表示文件里记录的校验和与重算结果不同；*unsure* 表示这次运行没法下结论：
要么该条原本只写了路径或写成 `<NONE> <路径>`（文件里没有可比较的校验和），要么根本
没能算出哈希（被中断、计算失败，或者算法就是 `none`）。两类路径会分别列在结果流里
对应计数的下面；写到 stderr 的那份报告不含它们。
校验和不同或 unsure **不会改变退出码**，只有
读取、写入和扫描错误才会，与 `sum` 一致——计算失败正属于后者，所以它仍然退出 1。
输出本身就是刷新过的清单，所以只要文件在此期间没有变化，对它再跑一次 `verify` 就会
得到 `Changed: 0`；在这份输出里仍是 `<NONE>` 的路径，下次再校验时归入 unsure。

`-v`、`-t`、`-k`、`-K`、`-o` 的用法与 `sum` 相同，`-u` 见上文。密钥算法必须重新提供
密钥，因为校验和文件只记录算法名，从不记录密钥。换了密钥算出的校验和完全不同，所以
给错密钥的表现是所有文件都变成 changed，而不是一条错误。用 `none` 写出的清单会被
拒绝（退出码 64），因为它没有任何可比较的校验和；用 `-u` 指定别的算法可以继续，而
`-u none` 虽然也能跑，但每条路径都会记入 unsure。`-o` 不能指向输入文件（退出码
64），否则输入会在被读取之前先被截断。

### 比较

`cmp` 读取两份由 `sum` 写出的结果文件，报告它们之间的差异：

```sh
tsubaki cmp old.txt new.txt               # 写出 old_to_new.cmp
tsubaki cmp old.txt new.txt -o -          # 把比较结果打到 stdout
tsubaki cmp old.txt new.txt -o diff.cmp   # 写到 diff.cmp
```

两份输入都用校验和文件格式：`#` 开头的行（包括整个报告块）忽略，其余每行都必须是
`<校验和> <路径>`。只写路径或写成 `<NONE> <路径>` 的行没有可比较的校验和，会记一条
错误并跳过。分隔符是两个空格，或空格加 `*`（二进制标记，不算路径的一部分）。两份
文件里最多只能有一个是 `-`（stdin）。校验和按小写十六进制比较，
所以大写写法不算变化。比较的只是校验和字符串：用不同算法（或不同密钥）写出的两份
清单没有一条能对上，于是每个路径都变成 modified，matched、moved、deleted 全都为空。

输出按差异的类别分节：

```
# tsubaki comparison result
# [!] Modified:
[!] ./chg.txt

# L = old.txt, R = new.txt
# [D] Moved,copied,merged or renamed:
# [D][1]
# [D][1][L]
[D][1][L]./mv.txt
# [D][1][R]
[D][1][R]./moved.txt

# L = old.txt, R = new.txt
# [U] Deleted or added:
# [U][L]
[U][L]./del.txt
# [U][R]
[U][R]./add.txt

# [=] Matched:
[=] ./same.txt
```

- `[!]` *Modified*（修改）：两边路径相同、校验和不同。打印的是左侧的写法。
- `[D][n]` *Moved, copied, merged or renamed*（移动、复制、合并或改名）：校验和
  相同但路径不同的条目，每个两边共有的校验和各成一组；`[D][n][L]` 列左侧路径，
  `[D][n][R]` 列右侧路径。只在一边出现的校验和不成组，那些路径归入删除/新增。
- `[U]` *Deleted or added*（删除或新增）：只出现在左侧（`[U][L]`）或只出现在右侧
  （`[U][R]`）、且在另一边没有同校验和路径的条目。
- `[=]` *Matched*（相同）：两边路径相同、校验和也相同。
- `[E]` *Error messages*（错误）：只在记录过问题时出现——某行没有校验和、`-c`
  无法把路径规范化，或者清单读取失败。比较会继续进行，此时的退出码是 1。

同一份清单里同一个路径重复出现、且校验和相同，只比较一次；同一个路径重复出现但
校验和不同，会按命令行错误拒绝（退出码 64），因为没有一个唯一的值可以比较。

不给 `-c` 时，路径按原样逐字比较，所以 `./a.txt` 和 `b/../a.txt` 是两个不同的路径。
给了 `-c`（`--canonical`）时，两边路径先经过 `std::filesystem::canonical()`，它会把
路径变成绝对路径、解析软链接并规整分隔符，因此指向同一文件的不同写法可以匹配上。
规范化要求路径存在：已删除的文件没法规范化，所以会保留未被规范化的路径并参与比较，
同时记录一条错误。

不给 `-o` 时，结果写到当前目录下的 `<左文件名去扩展名>_to_<右文件名去扩展名>.cmp`
（`old.txt` 和 `new.txt` 得到 `old_to_new.cmp`），并在 stderr 上提示这个文件名。
`-o -` 写往 stdout。`-o` 不能指向任何一份输入（退出码 64），因为两份清单都是在输出
打开之后才读的。各节之间重复出现的 `# L = ..., R = ...` 行标明两份输入；
开头还会往 stderr 打一份，这样结果写进文件时也能在终端上看到比的是哪两份。

`cmp` 不做任何哈希、遍历或扫描：它只读两个文件，所以下文的“中断”处理不适用于它，
`Ctrl-C` 会直接按默认动作结束进程。

## 输入

命令行上的文件与目录直接扫描。列表文件（`-l`，或 `-` 从标准输入读）逐行解析。
每一行都会先 trim，所以首尾空白不会变成路径的一部分：

- 空行、以 `#` 开头的行忽略；
- 以 `<NONE> `（标记加一个空格）开头的行，取标记后面的路径；
- `<校验和> <路径>` 形式的行原样保留，输出中打 `# Kept: <路径>` 加 trim 后的
  原行；只有给了 `--force-rescan` 才会按路径重算；
- 其它行整行都算路径，空格也算在内。

被保留的行与计算过程解耦：不参与哈希，也不出现在报告的计数里。它是在读列表时
就写进结果流的，所以可能夹在算完的行中间。

列表里的每一行都当作文件处理。行里写目录会被拒掉，不会展开；只有命令行上的目录
参数才会被遍历。以 `#` 开头的行即使本意是路径也算注释，所以名字以 `#` 开头的文件
要写成 `./#名字` 或绝对路径。

没有校验和的行本应整行当作路径，所以路径里可以带空格。但只要第一个空格前的部分是至少
32 个字符的纯十六进制（因此不可能含 `/`），这一行就没法和“校验和 + 路径”区分，一律
按后者解释。这是一份文件里同时接受两种格式必须付出的代价，所以这种路径要写成
`./名字` 或绝对路径；十六进制段更短、或整行没有空格时不受影响。

coreutils 用两个空格、或空格加 `*`（`sha256sum --binary` 的二进制标记）分隔校验和
与路径；那个 `*` 会被丢掉，永远不算路径的一部分，两种写法读出来完全一样。因为 `sum`
的输出用的是单个空格，以 `*` 开头的裸路径会被当成这个标记读回，所以这种文件要写成
`./*名字` 或绝对路径。

`<NONE> <路径>` 也能作为输入，所以一次运行的输出可以直接用 `-l` 喂回去，只重做
那些没有计算校验和的文件。

排除项是用 `equivalent()` 跟目录遍历中遇到的每个条目比较的，因此它既不是通配
模式，也不是字符串前缀。它只作用于目录扫描：命令行上直接给出的文件、或列表里
读进来的文件，即使被排除也照样计算。若排除项就是被扫描的目录本身、或它的某个
上级目录，则什么都匹配不到，会被静默忽略——要排除就排除子目录。也别用 `-e` 去
“排除”一个同时作为输入传进来的目录：不想要它，就别在命令行上写它。

命令行上或列表里显式给出的设备/FIFO 会被当作流打开并读完。所以 `/dev/null` 算出
的是空内容，`/dev/stdin` 算管道送来的东西，进程替换的 `/dev/fd/N` 也能用。这类流
可能阻塞或者永远不结束，见“中断”。socket 读不出内容，显式给出就是错误。目录遍历
则相反，只交出普通文件：遍历中遇到的设备、FIFO 或 socket 会被静默跳过，连一条错误
都不记，所以 `sum sha256 ~` 不会卡在别人留下的管道上。

路径不做去重：同一个路径写两次就处理两次。

稀疏文件按逻辑长度计算：空洞读出来就是零，所以只占几 MB 的 1 TB 稀疏镜像仍要读满
1 TB。

## 输出

结果默认写到 stdout，可用 `--output` 改到文件。结果流开头是一行
`# tsubaki checksum result`，之后每个文件一行：

```
<校验和> <路径>
```

（`cmp` 写的是 `# tsubaki comparison result` 和它自己的各节，见
[比较](#比较)。）

行的顺序是完成顺序，不是输入顺序，所以多线程下每次运行的顺序都可能不同。路径按
扫描器产出的原样打印：`.` 下面找到的条目带 `./`，列表里的条目则按原写法。

没算过的文件——被中断的、或者算法是 `none` 的——写成 `<NONE> <路径>`。已经通过
扫描、但打开/读取/哈希失败的文件也写成 `<NONE>`，并计入 Failed。

不存在的路径在取任务时就会被过滤掉：没有输出行，也不进下面任何一个计数，只往
错误块里加一条记录，但它一样会让退出码变成 1。列表里写的目录也按同样方式拒绝。

随后是报告块，每行都以 `#` 开头：

```
#
# ---------- Summary ----------
# Algorithm:         sha256
# Processed:         3
# Hashed:            3
# Failed:            0
# Not hashed:        0
# Duration:          1.23456 seconds
# Errors:            0
```

`Algorithm` 是本次运行选定的算法；它不会变，所以被打断的运行也照样写着当时在用的
算法。`Duration` 量的是从启动工作线程到 join 结束，不含参数解析和扫描准备。

`Processed` 等于 `Hashed + Failed`，未计算校验和的文件不计入；被保留的行和跳过
的路径也不算在内。

`# Errors:` 条数行总会打印，即使为 0 也在。被打断的运行会在条数下面多出一个 `#`
分隔行和一行 `# Warning: The process was interrupted halfway through.`；记录过至少
一条错误时，后面还会跟一个 `# Error messages:` 块，每条一行
`# Value: / Message: / Operation:`：

```
# Errors:            2
#
# Error messages:
# Value: 2, Message: No such file or directory, Operation: determining the file type of plain.txt
```

错误不一定来自计算失败：不存在的输入路径、打不开的列表文件、不存在的排除项等
非阻断性错误都会记在这里，所以一次运行的 `Failed` 可以是 0、退出码却是 1
（而且不存在的排除项虽然报错，扫描本身照常继续）。

用 `--output` 时，报告块还会额外写一份到 stderr（不含逐条错误信息），这样结果
进文件、简短摘要在终端上也会输出一份。

进度指示只写 stderr，不混进结果流。

程序在最后会使用 `std::ostream::fail()` 检查写错误。工作线程的每一行都经
`std::osyncstream` 完整刷出，报告在工作线程 join 之后写入；刷出失败——
磁盘写满、描述符损坏、文件所在挂载点被移除——会在流上留下失败状态，
退出码是 `73`。若结果写往读端已关闭的管道，写入会触发 `SIGPIPE`，进程按默认动作
直接结束（shell 报 141），走不到 `73`。

## 退出状态

| 退出码 | 含义                                                                                                                                      |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `0`    | 没有记录任何错误；`verify` 会把 changed/unsure 报出来、`cmp` 会把所有差异报出来，但都不当作错误 |
| `1`    | 记录过至少一条错误：校验失败、不存在的路径、打不开的列表文件、不存在的排除项；`cmp` 还会把没有校验和的清单行、`-c` 无法规范化的路径、清单读取失败记为错误 |
| `64`   | 命令行无效：未知子命令、未知算法、密钥算法没给密钥或密钥过长、`-k` 与 `-K` 同时给、`-K -` 与 `-` 输入同时出现、线程数不对，或者有多余参数；`verify` 还会在没有 `-u` 时对没有 `Algorithm:` 头的输入、对没配 `-u` 的 `-` 输入、对用 `none` 写出的清单、对未知的 `-u` 名字、以及输出指向输入文件的情况返回 64；`cmp` 在两份清单都是 stdin、输出指向其中一份清单、或同一份清单里同一路径带着不同校验和重复出现时返回 64 |
| `66`   | `--key-file` 读不了、密钥文件里没有密钥，`verify` 的输入不存在或是个目录，或者 `cmp` 的清单读不了 |
| `70`   | 启动即失败：`argc` 为 0，进程拒绝运行                                                                                                     |
| `73`   | `--output` 指定的文件打不开，或者输出流错误。                                                                                             |
| `130`  | 运行被 `Ctrl-C` 打断                                                                                                                      |
| `250`  | 按下五次 `Ctrl-C`，进程当场中止，不保证输出结果的完整性。                                                                                 |
| `255`  | 有异常逃出了 `main()`，说明存在开发者未考虑到的 bug，可以提交 issue。                                                                     |

`--help` 和 `--version` 的退出码是 `0`。`64`、`66`、`70` 和 `73` 取自 sysexits
的 `EX_USAGE`、`EX_NOINPUT`、`EX_SOFTWARE` 和 `EX_CANTCREAT`；`130` 就是 shell 的
`128 + SIGINT`；`250` 与意外异常使用的 `255` 差一格，两者不会混。

这些码定义在 `include/exit_codes.hpp` 里：`TSUBAKI_SUCCESS`、`TSUBAKI_HASH_ERROR`、
`TSUBAKI_INVALID_OPERATION`、`TSUBAKI_FILE_WRITE_FAILED`、
`TSUBAKI_FILE_READ_FAILED`、`TSUBAKI_INTERRUPTED`、`TSUBAKI_TERMINATED`、
`TSUBAKI_FATAL` 和 `TSUBAKI_UNEXPECTED`。

## 中断

第一次 `Ctrl-C` 会置上 manager 的中断标志。工作线程在处理下一个文件之前就停下：
还没开始的文件照样被取出，写成 `<NONE>` 并计入 `Not hashed`，因此报告能为扫描器
产出的每个文件留个交代。已经进入计算函数的文件不会被丢掉；如果那是设备或 FIFO，
就意味着它可能一直读到 EOF。而卡在 `open()` 或无限读取里的工作线程根本回不到检查点，
所以一次 `Ctrl-C` 停不下它。

这让中断可以续算：把那次的结果文件直接当 `-l` 的输入喂回去，已经带校验和的行原样
保留，`<NONE>` 行重新计算。报告块以 `#` 开头会被忽略，所以结果文件不用先过滤。
被中断的运行即使没有任何失败，退出码也是 `130`，所以 `1` 仍然代表真的出错。

累计按下五次 `Ctrl-C` 则彻底放弃：处理函数往 stderr 写一行固定消息，并当场调用
`_exit(250)`。此后什么都不再刷出，所以输出可能没有报告块，计数也一并丢失。

## 来由与范围

Tsubaki-Next 是早先 Tsubaki 的精神续作。已归档的
[Lawrence-Charland/Tsubaki](https://github.com/Lawrence-Charland/Tsubaki) 里并排放着
两套各自独立的实现：`old` 分支是本项目作者自己写的，`main` 分支是 GDJT-DSR 写的。
那个仓库已经归档；[GDJT-DSR/Tsubaki](https://github.com/GDJT-DSR/Tsubaki) 仍在
维护。

本项目只构建一个可执行文件 `tsubaki`，而且会一直如此。新功能以**子命令**的形式加
进这个二进制，而不是再开新目标：目前有 `sum`、`verify` 和 `cmp` 三个子命令。

`sum` 和 `verify` 是流式的：一次只计算或比较一个文件，不需要把整份清单读进内存。`cmp` 则是例外：
它把两份清单都读进内存，等两边都到齐了才开始下结论。

## 路线图

计算流水线保持单向：一条路径算完就写出去，从不收集。`cmp` 是反过来的形状，也不建在
那条流水线上：它把两份清单读进内存，两边都载入之后才比较。除了这三个子命令，暂时
没有别的设计。

`timeline_fs` 曾是为“让两份以上的结果可以相互比较”画出的结构：一棵内存树，每个节点
各自带一份**按快照区分**的子节点表和一份按快照区分的校验和表。先按名字登记一个
时间 id，再在那个 id 下建目录、建文件、更新或删除。载入任意多个 id 并同时遍历这棵
树，就能看出各次运行之间变了什么；同一张表也能看出哪些文件内容相同。

`timeline_fs` 的开发已暂停，源码作为实验保留在
[experiments/timeline_fs/](experiments/timeline_fs/) 而不是源码树里：没有任何目标
引用它，`cmp` 也不用它——它是两份清单之间的两两比较。模块划分本身见
[ARCHITECTURE.zh-cn.md](ARCHITECTURE.zh-cn.md)。
